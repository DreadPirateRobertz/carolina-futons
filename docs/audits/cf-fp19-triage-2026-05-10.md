# cf-094q (cf-fp19) — MAYBE-CFW-NAME-COLLISION triage

**Bead**: cf-094q · **Author**: cfutons/crew/morgott · **Date**: 2026-05-10 · **Source**: PR #1320 (`cf-hpwy v3.2 snapshot`)

## Goal

The cf-hpwy v3.2 detector classified 19 webMethods as `MAYBE-CFW-NAME-COLLISION`: cfw has bare-name references but no `from backend/<X>` import. Per-method audit to confirm true-FP (cfw same-name local function) vs real cfw consumer the detector missed, and identify any retirement candidates.

## Methodology

For each method:
1. Grep cfw for bare-name hits.
2. Check whether any cfw file declares the name locally (`function <name>` / `const <name> = ...` / `class <name>` / `export function <name>`).
3. Check for any `from .*backend/<modfile>` static import in cfw.
4. Check for any `callVelo({method: '<name>'})` or `_functions/<name>` URL reference in cfw.
5. Cross-reference with the v3.2 detector's other-surface flags (FRONTEND, INTERNAL, FILESYSTEM-PATH-REFERENCED) to see whether the webMethod is alive via Velo-side consumers regardless of cfw status.

## AMBIGUOUS-FP-CONFIRMED-VIA-OTHER-SHAPE (2)

Each has cfw bare-grep hits that resolve to a non-callVelo shape, AND has no real Velo-side consumer either. **Truly dead.**

### `sendRecoveryEmail` — `src/backend/cartRecovery.web.js:190`

cfw hits (3):
- `src/app/api/auth/forgot-password/route.ts:25` — error log string `"sendRecoveryEmail failed"`
- `src/lib/wix/auth.ts:5` — JSDoc comment text `"recovery.sendRecoveryEmail"`
- `src/lib/wix/auth.ts:13` — `client.recovery.sendRecoveryEmail(email, ...)` — **method on the Wix SDK's `recovery` namespace** (forgot-password flow), not the Velo cartRecovery webMethod.

Velo-side cfutons/stage3 callers: zero real callers. Only hit is a JSDoc reference in `couponsService.web.js:280` ("called internally by sendRecoveryEmail; not intended for direct client use") — comment text describing the deleted method's documented role, NOT an invocation.

**Disposition**: **DEAD — drop in this PR**. Plus the dead JSDoc comment in couponsService.

### `updateWishlistStock` — `src/backend/wishlistService.web.js:255`

cfw hit (1):
- `src/__tests__/server-actions.test.ts:44` — negative-assertion test: `expect("updateWishlistStock" in mod).toBe(false)`. The test EXPLICITLY asserts that `updateWishlistStock` is NOT exported on the cfw side.

**Disposition**: **DEAD — drop in this PR**. Plus the cfw negative-assertion test stays as-is (it'll continue to assert truthfully after the Velo retirement).
